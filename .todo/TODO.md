  1. **Backup primero (rollback primario):** `supabase db dump` del dev remoto **antes** del push → snapshot SQL completo para restaurar si algo sale mal. Dev está en tier free (sin PITR/backups automáticos), así que el dump manual es la red de seguridad real.
  2. **Down-migration (rollback secundario):** escribir y **probar** el SQL inverso (drop de tablas/funciones/trigger/políticas nuevas + restaurar valores viejos de `usuarios.rol`). Ojo: lo difícil es revertir la **transformación de datos** de `rol` (matriz vieja hardcodeada → keys dinámicas); el dump cubre eso mejor que el down-SQL.
  3. **Ensayo local (repetible):** usar `supabase db reset` para re-aplicar todo desde cero. Sembrar el local con un estado que imite el **pre-migración** de dev (usuarios con los roles viejos), aplicar la migración, correr el e2e + checks manuales, y **practicar el rollback** (restore del dump / correr el down-SQL). Repetir hasta que salga fluido.
  4. **Secuencia para dev (día del PR):** link a dev → `db dump` (backup) → `db push` → verificar (e2e/manual) → si rompe, restaurar del dump. Recién entonces abrir el PR a `development`.
